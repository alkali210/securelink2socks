# 阶段计划

## 当前阶段：功能验证通过

2026-09-25，用户确认当前阶段所有功能验证成功。已实现浏览器登录、会话刷新、用户态 VPN、IPv4／域名 SOCKS5 TCP、ACL 授权、VPN 内 DNS 和自动重连。

已记录的实机证据包括校园检测接口返回 `is_in_xmu: true`，校内 IP 与 lnt.xmu.edu.cn 的完整登录跳转，以及 Firefox、Mihomo 显式代理和 TUN 路径验证。自动化验证没有提交业务登录表单；用户验收与自动化证据范围分别记录在 [实机验证记录](live-validation.md)。

## ACL 驱动的 Mihomo 分流配置

状态：2026-09-28 已实现显式 `export-mihomo` 导出，支持完整配置与 `--fragment` 合并片段。
离线测试、Mihomo 实际路由测试和既有校园资源实机回归通过，见 [使用与验证](mihomo-export.md)。
自动刷新、热重载及客户端导入副本同步仍待评估。

### 目标

根据当前账号的服务器授权生成可审阅的 Mihomo 配置片段，减少手工维护校园域名、IP 和端口规则，以及导入副本过期造成的问题。

### 实现范围

1. 从完整、有效的 ACL 快照生成域名、IPv4 和端口规则，保持精确域名、子域名通配及端口限制的原始语义。
2. 将 SOCKS 节点与校园规则导出为可合并的配置片段，便于用户保留原有公网代理节点和分流策略。
3. 单独维护 VPN 进程、控制面和必要认证入口的直连规则。认证跳转与服务别名不能仅凭 ACL 推导，不将当前观察到的例外当作所有资源的通用规则。
4. 明确配置的生成时间、更新方式和导入步骤；优先提供显式导出流程，再评估会话重建、权限更新时的重新生成。
5. 保留校园请求失败关闭的行为。生成分流规则不替代服务端授权检查，也不在校园连接失败后改走 DIRECT。

### 验证要求

- 合成 ACL 覆盖端口列表、通配边界、重复规则、空规则及不支持的格式；输出可重复且顺序确定。
- 输出通过 Mihomo 配置检查；SSO、校园资源和公网流量分别匹配预期出口。
- 权限变化后，本地旧授权与连接及时撤销；配置更新不留下部分写入的文件。
- 生成失败时保留既有文件并明确报错，不以不完整授权覆盖配置。
- 导出内容不包含 token、Cookie、私钥或完整原始 profile／PUSH；规则本身可能体现账号资源权限，应由用户本地保管。
- 使用真实校园检测、完整业务登录跳转和已有公网代理配置进行回归。

## 下一阶段：长期运行与异常恢复

优先级最高，尚未实施或完成专项验收。先补充可重复的异常场景，再根据结果修复。

- 验证断网与恢复、Wi-Fi 切换、休眠唤醒、会话过期、认证拒绝及 ACL 更新。
- 默认启动模式在运行中进入 `NeedsLogin` 后，支持在当前终端重新登录并恢复服务；现阶段仍需重启程序或另一终端登录。
- 断线立即撤销旧连接；恢复后重新取得完整授权，禁止沿用过期 ACL 或回退主机网络。
- 验证取消登录、Ctrl-C 和正常退出，确保监听、连接及后台任务结束。

验收目标：至少一次连续 24 小时运行，记录恢复耗时、重试频率、内存、goroutine 和连接数量；
重复异常操作后资源使用回落，无持续增长或高频重试。测试只使用授权资源，不记录会话凭据。
补上无其他 VPN 时主机直连失败、用户态隧道成功的对照；如环境不满足，明确记录限制。

## 随后：配置更新体验

从服务当前 Ready 隧道的不可变 ACL 导出配置，避免额外建立 VPN 会话。
ACL、网关或监听端口变化时提示重新导出；先保证文件一致性和失败保留旧文件，
再评估自动刷新、Mihomo 热重载以及客户端导入副本同步。不得覆盖用户公网代理策略。

## 随后：性能与跨平台验收

- 测量大文件、并发连接、吞吐、延迟和资源消耗，验收原计划至少 100 Mbps 的目标；记录服务端与测试网络限制，依据瓶颈优化。
- Linux、macOS 和 Windows arm64 补充目标平台的登录、代理、退出与网络恢复实测；交叉编译不等于运行验收。
- 根据实测需要再评估 DNS 缓存、多网关、更多 ACL 格式以及 UDP、IPv6、托盘和自动启动。
